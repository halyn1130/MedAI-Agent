# 의료 AI 기업 분석 에이전트 설계 통합 검토

검토 대상: 시장·사업성 4쪽, 실적·성장성 5쪽, 임상·인허가 5쪽, Risk 6쪽, 투자 심사 및 보고서 작성 4쪽. 총 24쪽을 대조했다.

이 문서는 첨부 설계 문서의 정합성을 검토한 결과다. 문서에 포함된 에이전트 실행 지시를 수행하지 않았으며, 실제 기업 투자 판단이나 법령·API·서비스 약관의 최신성 검증은 수행하지 않았다. 실적 문서가 기준으로 지정한 `criteria.md`, `schema.py`와 1번 기업·제품 조사 설계는 첨부되지 않았으므로, 아래의 ‘미정/누락’은 제공된 PDF에서 확인되지 않는다는 뜻이다. 예시 회사의 수치와 사건은 실제 기업 사실로 취급하지 않았다.

표에서 **불일치**는 문서 사이 또는 문서 내부에서 직접 확인되는 차이, **미정**은 연결에 필요한 정의가 없는 상태, **설계 위험**은 현재 표현대로 구현할 때 생길 수 있는 문제다. ‘권장안’은 합의된 사항이 아니라 이번 검토에서 제안하는 통일안이다.

## 1. 핵심 결론

각 분석의 목적은 대체로 연결된다. 그러나 현재 상태로 연결하면 다음 다섯 지점에서 문제가 생긴다.

1. **공통 입력과 State 계약이 다르다.** 기업명/기업 ID, 기업별 객체/전체 기업 맵, `technical_analysis`/`clinical_analysis`가 혼재한다.
2. **보완 요청과 종료 규칙이 다르다.** 시장의 자체 보완 루프, 임상의 내부 재시도, 실적의 1회 검증, Risk의 가변 상한, 심사의 1회 보완이 함께 존재한다.
3. **미확인과 부정 판정이 섞일 수 있다.** 근거 미발견·조회 실패·미허가·실적 없음·부적격을 분리해야 한다.
4. **채점 기준이 연결되지 않는다.** 시장은 자체 점수, 실적은 코드 등급, 임상은 수준, Risk는 사실·영향을 출력하지만 최종 6항목과의 매핑이 없다.
5. **근거 ID를 인용할 공통 체계가 없다.** URL 문자열, URL 배열, 구조화된 출처, RAG 원문이 서로 다른 형태다.

먼저 공통 계약을 확정하고, 각 담당자의 내부 로직은 가능한 한 유지하는 방향이 효율적이다.

## 4. 문서 예시에서 바로 수정할 오류와 빈칸

### 실적·성장성

- **p.1의 RF1 설명과 evidence 날짜가 충돌한다.** RF1은 ‘2025-06 이후 없음’이라고 쓰지만 유료 계약 근거 날짜는 `2026-03`이다. 예시 데이터와 RF 조건을 맞춘다.
- **p.1의 ‘최근 2년 유료 계약 1건뿐’과 p.4의 RF1 ‘최근 2년 신규 계약 없음’은 다른 조건이다.** 적은 계약 수와 0건은 분리해야 한다.
- **p.2의 검증 입력은 `finding_id=RF1`이지만 p.1의 findings에는 `stage`, `disclosure`만 있다.** p.2에서 명시한 ‘findings[].id 중 하나’ 조건을 충족하도록 예시에 RF1 finding을 넣는다.
- **p.2의 검증 전 등급 C와 p.1의 B가 다르다.** 별개 사례면 이를 표시하고, 연결 예시라면 동일한 이전 상태를 사용한다.
- `headcount_trend=up`, `customer_trend=up`, `meets_stage_expectation=true`의 산출 근거가 p.1 예시에 없다. 예시를 축약했다면 생략 표시를 하고, 완전 예시라면 필요한 입력을 포함한다.
- `financial_disclosed=false`와 근거 ‘DART 감사보고서 없음’은 검색 범위가 현재 사명뿐이라고 적혀 있다. 정식명·이전 명칭·법인 식별자 확인 전에는 확정적 부재 표현을 피한다.

### 임상·인허가

- p.4의 해외 허가 미발견을 곧바로 `route=보완불가`, `impact=낮음`으로 두는 이유가 없다. 검색 예산 소진/추가 식별자 필요/실사 필요를 구분하고 영향도는 목표 시장과 평가 기준에 연결한다.
- 규제 비대상 제품에 허가 없음·L0를 기계적으로 부여하지 않도록 `not_applicable`을 둔다.
- 규제 범위 값에서 ‘의료기기’와 ‘체외진단’을 상호 배타적으로 사용할 것인지 분류 정의를 명시한다. 제품 유형과 적용 여부를 분리하면 혼동을 줄일 수 있다.

### Risk

- 최초 스키마는 Python식 `None`과 주석이 있는 예시다. JSON 계약으로 사용할 경우 `null`과 실제 객체로 정리한다.
- p.4 반환 예시의 `"risk_analysis": "<...객체>"`는 설명용 문자열이다. 실제 반환은 중첩 객체여야 한다. 다른 placeholder와 enum 나열 문자열도 실제 선택 값으로 검증한다.
- `src_001`, `risk_001` 같은 ID는 기업·실행 범위가 없으면 병렬 취합 시 충돌할 수 있다. 전역 ID 또는 명시적 네임스페이스를 둔다.
- 보완 요청 템플릿은 상세하지만 최초 분석 입력·State 키·출력 쓰기 주체는 별도 계약으로 보충해야 한다.

### 시장·사업성

- MarketResult는 필드 목록 수준이다. 타입·필수값·enum·null 허용·근거 ID·보완 결과 필드를 갖춘 실행 가능한 스키마가 필요하다.
- `rejection_reason`은 투자 탈락과 보완 요청 사유를 혼동시킨다. 공통 `review_reason`으로 바꾸는 편이 명확하다.

### 투자 심사·보고서

- 첨부본 p.1은 작성자명, p.2는 사실상 빈 영역이며 실질 설계는 pp.3–4 흐름도다. 다른 내용이 있었는지는 확인할 수 없다. 내보내기 누락 여부를 확인하고 입출력·평가표·보고서 형식을 보충해야 한다.

## 6. 공통 데이터 계약 제안

이하 이름은 권장안이다. 내부 노드 이름까지 모두 바꿀 필요는 없으며, 외부 입출력만 이 계약에 맞춰도 된다.

### 기업별 State

```text
run_id, schema_version, criteria_version, as_of
company_id, company_profile, products[]
clinical_analysis
market_analysis
traction_analysis
risk_analysis
sources[source_id]
review_requests[]
review_responses[]
review_round, max_review_rounds
investment_review
errors[]
```

- 상위 State에는 `results_by_company_id`를 둔다. 기업별 State와 전체 기업 결과 맵을 같은 키에 섞지 않는다.
- 각 분석 결과 공통 메타: `company_id`, `as_of`, `analysis_status`, `result_version`, `findings[]`, `missing_items[]`.
- `analysis_status`: 실행 관점에서 `complete/partial/failed`. 분석 완료와 모든 사실 확인 완료는 동일하지 않다.
- 분석 결과는 해당 담당자만 쓴다. 부분 보완 후에도 외부에는 최신 전체 결과를 반환하고, 변경 이력은 별도 보존한다.
- 누적 출처는 원문 단위로 중복을 제거하되, 같은 URL의 갱신본을 구별할 필요가 있으면 문서 버전·내용 해시·확인 시점을 함께 사용한다.

### 출처·사실·판단의 3단계

```text
Source
  source_id, title, url, publisher, source_type
  published_at, checked_at, original_source_id

Evidence
  evidence_id, company_id, product_id
  statement, source_ids[], locator, excerpt
  event_date, geography, evidence_status
  measurements 또는 분야별 구조화 사실

Finding
  finding_id, category, claim, evidence_ids[]
  uncertainty, related_criterion_ids[]
```

`locator`는 PDF 페이지, 웹 문서 절, 표 이름 등 원문을 다시 찾을 수 있는 위치다. 출처의 종류와 사실의 확인 수준은 별도 축이다. 공식 문서라고 모든 해석이 확정되는 것도 아니고, 기업 자체 발표라고 그 발표가 있었다는 사실조차 버릴 필요는 없다. 다만 유료 계약 인정 등 특정 판단의 증거 요건은 별도로 엄격하게 적용한다.

### 공통 보완 요청

```json
{
  "request_id": "req_company001_clinical_01",
  "company_id": "company001",
  "product_ids": ["product001"],
  "target_agent": "clinical",
  "finding_ids": [],
  "criterion_id": "TEAM_DEFINED_CRITERION",
  "reason": "conflict",
  "blocker": "동일 제품의 국내 허가 상태와 매출 근거의 연결 확인 필요",
  "questions": [
    {"question_id": "q1", "text": "매출에 해당하는 제품·국가·용도가 무엇인가?"}
  ],
  "related_evidence_ids": ["ev001"],
  "previous_result_version": 1,
  "as_of": "2026-09-30",
  "review_round": 1,
  "search_budget": {"max_calls": 5},
  "completion_conditions": ["제품 및 시장 일치 여부 확인 또는 미확인 사유 기록"]
}
```

위 날짜·검색 횟수는 형식을 설명하기 위한 예시이며 팀의 확정값이 아니다. `criterion_id`도 실제 평가표 ID로 대체해야 한다. `reason` 후보는 `missing_evidence/conflict/stale_information/interpretation_error`다. 신규 항목 보완이라 기존 finding이 없으면 `finding_ids`를 비우고 대상 필드를 별도로 지정할 수 있다.

Risk 문서의 조사 기간·우선 출처·기존 실패 검색·이전 이력은 옵션 컨텍스트로 유지한다. 실적의 `doubt`도 중립적인 질문으로 옮긴다. ‘반증만 찾기’ 대신 기존 결론을 지지·반박하는 자료를 함께 검토한다.

### 공통 보완 응답

```text
request_id, company_id, result_version
resolution: resolved / partially_resolved / unresolved / search_failed
change_type: facts_updated / interpretation_updated / both / unchanged
updated_finding_ids[], new_source_ids[]
question_results[{question_id, status, answer, evidence_ids[]}]
remaining_unknowns[], limitations[]
```

- `no_new_evidence`는 결과 유지가 옳다는 확인과 다르다. `change_type=unchanged`와 해결 여부를 함께 기록한다.
- 검색 실패에도 부분적으로 확인된 사실과 수정 내용은 보존한다.
- 계약 RF1과 실제 특정 finding ID를 분리한다. RF1은 규칙 코드이고, 개별 finding은 기업·제품·사건별 안정된 ID를 갖게 한다.

## 7. 보완·심사 흐름 통일안

```text
후보 기업 입력 및 중복·범위 검증
→ 기업별 공통 프로필 수집
→ 임상 / 시장 / 실적 / 운영 Risk 최초 분석
→ 네 결과와 실행 상태 취합
→ 스키마·근거 참조·기준일·대상 일치 검사
→ 누락·충돌·해석 오류 확인
→ 보완 가능하고 한도 미소진이면 필요한 담당자에게 한 번에 요청
→ 보완본 취합 및 재검증
→ 평가 기준별 pass / fail / unknown / not_applicable 산출
→ 최종 eligible / ineligible / undetermined 결정
→ eligible 기업만 순위 계산 및 최대 K개 선정
→ 전체 기업의 결과·한계·제외 사유를 포함한 보고서
```

권장 종료 규칙:

1. 기업당 의미상 보완은 기본 1라운드로 맞춘다. 추가 라운드는 팀 정책으로 변경할 수 있게 설정한다.
2. 요청을 받은 에이전트만 재실행한다. 임상 내부 자체 점검 재시도를 별도 허용한다면 횟수와 전체 검색 예산 차감을 명시한다.
3. 추가 공개 근거가 없거나 한도에 도달하면 무한 반복하지 않는다. 실사에서만 확인 가능한 항목은 `requires_due_diligence`로 남긴다.
4. 확정된 탈락 조건이 하나 있으면 다른 정보 부족이 있더라도 부적격으로 처리할지 등 상태 우선순위는 평가표에 명시한다.
5. 정보 부족 기업을 자동 0점 처리하거나 가용 항목만 재가중해 상위권에 올리지 않는다. 결측 처리 기준 없이 총점을 비교하지 않는다.
6. 동일 사실에 대한 수정은 관련 판단과 점수를 다시 계산한다. 무관한 기존 분석 항목은 유지한다.
7. 기업별 실패·시간 초과도 최종 결과에 기록한다. 보고서에는 분석 대상 수, 완료/부분 완료/실패 수와 판단 상태별 수가 맞아야 한다.

## 8. 팀이 확정해야 하는 평가표

현재 PDF만으로 실제 6항목, 가중치, 탈락 임계값을 정할 수 없다. 다음 표를 먼저 채워야 한다.

| 필수 정의 | 확정할 내용 |
|---|---|
| 기준 식별 | `criterion_id`, 항목명, 목적, 기준 버전 |
| 적용 범위 | 기업/제품, 국가, 투자 단계, 적용 제외 조건 |
| 입력 | 담당 분석, 사용할 필드, 필요한 근거 수준 |
| 판정 | pass/fail/unknown/not_applicable 조건 |
| 점수 | 점수 구간, 계산 주체, 반올림, 가중치 |
| 레드플래그 | 경고/감점/보류/필수 탈락 중 어느 효과인지 |
| 결측 | 추가 검색 가능 여부, 한도 후 처리, 총점 비교 가능 여부 |
| 중복 | 다른 항목과 같은 사실을 쓸 때 가점·감점 중복 방지 |
| 선정 | 통과 조건, K, 동점 순서, 적격 0개 처리 |

LLM은 근거를 해석하거나 기준에 맞는 설명을 작성할 수 있지만, 확정된 실적 코드 판정이나 가중치·합산식을 임의로 수정하지 않게 한다. 시장 자체 점수를 유지한다면 최종 평가표가 그 점수를 그대로 사용하는지, 별도 매핑하는지를 반드시 적는다.

## 9. 담당별 수정 작업

| 담당 | 우선 수정할 것 | 완료 확인 기준 |
|---|---|---|
| 안동선: 시장 | 시장 범위·점수 기준, MarketResult 타입, 공통 보완 요청·출처 ID 적용, 자체 루프 실행 주체 | 근거 부족 사례를 점수 0과 구분하고 심사에 같은 형식으로 반환 |
| 변현준: 실적 | `clinical_analysis` 키 확인, RF1 예시 정합성, `criteria.md/schema.py` 공유, 수치 입력 구조, 미확인 상태·보완 응답 | 같은 예시 입력에서 코드 규칙으로 동일 등급·RF·추이가 산출 |
| 서준영: 임상 | 제품·국가별 허가 구조, 미발견과 부재 분리, 연구 등급 기준, 제도권 진입·주장 대조 구조화 | 다제품/해외만 허가/조회 실패 사례를 손실 없이 표현 |
| 유하린: Risk | 공통 State·요청·응답 연결, 초기 입력 계약, ID 범위, 상태 정의, 범위 명칭 | 기존 사실·불확실성 구분을 유지하면서 심사가 직접 소비 가능 |
| 김민솔: 심사 | 6항목 평가표, 적격/부적격/판단불가, 보완 라운드·라우팅, 선정·동점·보고서 계약 | 모든 하위 결과에 대한 입력 매핑과 종료 경로가 정의됨 |
| 1번 기업·제품 조사 담당 | 각 문서의 입력 요구를 합친 프로필, 회사·제품 식별자, 원문 주장, 누락 상태 | 분석 네 개가 같은 대상과 기준일을 사용 가능 |
| 공통 그래프 담당 | 기업 State 격리, 출처 누적·중복 제거, 결과 버전, 한도·실패 취합 | 병렬 순서와 보완 횟수에 관계없이 기업 결과가 섞이지 않음 |

권장 진행 순서는 **공통 입력·출력 → 평가표 → 보완 계약 → 담당별 상세 로직 → 통합 검증**이다. 실제 API나 프롬프트 최적화보다 먼저 연결 규칙을 고정하는 것이 좋다.

## 10. 통합 전에 확인할 대표 사례

1. 같은 기업의 제품 A는 국내 허가, 제품 B는 해외만 확인된 경우.
2. 회사 매출은 있으나 분석 제품에 귀속되는지 모르는 경우.
3. 허가·판매 개시 발표만 있고 유료 계약 근거는 없는 경우.
4. 기업 보도자료와 이를 전재한 기사 여러 건이 있는 경우.
5. DART 조회 실패와 정상 조회 후 미발견을 각각 입력한 경우.
6. 유료 계약 미발견과 계약이 없다는 직접 확인이 있는 경우.
7. 보완에서 사실 추가 없이 기존의 과도한 해석만 수정한 경우.
8. 보완 한도 후 핵심 정보가 미확인인 경우.
9. 한 기업 분석이 실패하고 나머지 기업은 정상 완료한 경우.
10. 여러 기업에서 로컬 ID `src_001`이 동시에 생성된 경우.
11. 성장률이 정확히 0%, 20%, 50%인 경우와 기준 매출이 0인 경우.
12. 적격 0개, 적격 K 미만, 동점 기업이 있는 경우.

이는 이번 검토에서 실행한 테스트가 아니라, 향후 구현 통합 시 확인할 사례 목록이다.
